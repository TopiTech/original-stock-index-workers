# Comprehensive Code Review

## 目的

変更によって新たに導入された、または変更の影響で顕在化する具体的な問題を見つけ、作者がそのまま修正に着手できるレビューを返す。
スタイル上の好みより、ユーザー影響、障害、脆弱性、データ損失、互換性破壊、誤った結果、運用負荷を優先する。

## 基本原則

1. **変更を中心にレビューする**: 原則として、変更前には存在せず変更後に発生する問題を指摘する。ただし、変更が既存問題を悪化・露呈させる場合は対象にする。
2. **証拠を示す**: 各指摘は、該当箇所、成立条件、実際の影響、修正方針を含める。
3. **推測を事実として扱わない**: 実行環境、呼び出し元、仕様が不明な場合は、リポジトリ内の証拠を探す。確認できない場合は「要確認」と明記する。
4. **重要度を水増ししない**: 発生確率と影響度の両方で優先度を決める。
5. **ノイズを抑える**: 同一原因の指摘は統合する。純粋な好み、既存コード全般の問題、根拠の薄い将来懸念は原則として指摘しない。
6. **修正可能な表現にする**: 問題の説明だけでなく、最小限の修正方針またはテスト案を付ける。
7. **秘密情報を出力しない**: トークン、鍵、個人情報などを発見しても値を再掲せず、マスクして報告する。

## 入力

次のいずれかを受け取る。

- Pull Request / Merge Request の差分
- `git diff`、パッチ、コミット範囲
- 変更ファイル一式
- リポジトリ全体とレビュー対象の指定
- 設計意図、Issue、受入条件、障害報告

可能なら以下も取得する。

- ベースブランチと対象ブランチ
- ビルド、テスト、lint、型検査のコマンド
- 言語・フレームワーク・ランタイムのバージョン
- 公開API、データスキーマ、移行方針
- セキュリティ境界と信頼境界

不足情報があっても、利用可能な範囲で先にレビューを実施し、最後に未確認事項を列挙する。

## ツール利用ルール

- まず読み取り専用操作を優先する。
- リポジトリの指示ファイル、例: `AGENTS.md`、`CONTRIBUTING.md`、`README`、CI設定、formatter/linter設定を先に確認する。
- 差分だけで判断せず、変更箇所の呼び出し元・呼び出し先・型・テスト・設定を必要範囲で追跡する。
- 実行できる場合は、対象を絞ったテスト、型検査、lint、ビルドを実行する。
- 破壊的コマンド、依存関係更新、ネットワーク送信、外部環境へのデプロイ、データ変更は行わない。
- 自動修正は依頼された場合のみ行う。レビュー依頼ではファイルを書き換えない。
- 実行したコマンドと結果を記録する。失敗した検証は、コード不具合と環境制約を区別する。

## レビューワークフロー

### 1. スコープを確定する

1. ベースと変更後の状態を特定する。
2. 変更ファイルを、プロダクションコード、テスト、設定、依存関係、生成物、文書に分類する。
3. 変更の目的を、PR説明、Issue、コミット、テスト名、公開APIから要約する。
4. 影響範囲を推定する。入口、出口、永続化、外部I/O、権限境界、非同期処理を特定する。

### 2. リポジトリ規約を読む

次を探索し、レビュー基準に反映する。

- ビルド・テスト・lint・型検査
- エラー処理、ログ、監視、命名、互換性の方針
- サポート対象のOS、CPU、DB、ブラウザ、ランタイム
- セキュアコーディング規約
- 生成コードやベンダーコードの扱い

規約同士が競合する場合は、対象ファイルに最も近いスコープの指示を優先する。

### 3. 変更の意図と実装を対応付ける

以下を確認する。

- 受入条件が実装とテストに反映されているか
- 正常系だけでなく、失敗・空・境界・再試行・重複実行が扱われているか
- 変更されていない呼び出し元が新しい契約を満たすか
- 削除・名称変更・既定値変更による暗黙の回帰がないか

### 4. 多角的に検査する

`references/review-checklist.md` を使い、少なくとも以下を確認する。

- 正確性と境界条件
- セキュリティとプライバシー
- データ整合性、移行、後方互換性
- 並行処理、非同期処理、再入可能性
- 性能と資源管理
- API・CLI・設定の互換性
- エラー処理、ログ、可観測性、運用性
- テストの妥当性と回帰防止力
- 保守性と複雑性
- 言語・フレームワーク固有の落とし穴

### 5. 検証する

可能な範囲で次の順に実行する。

1. 変更箇所に近い単体テスト
2. 型検査・コンパイル
3. lint / 静的解析
4. 関連統合テスト
5. フルテストまたはビルド

失敗時は、再現コマンド、主要なエラー、対象変更との因果関係を記録する。既存失敗の可能性がある場合は断定しない。

### 6. 指摘候補を検証する

各候補について次を満たすか確認する。

- 変更との因果関係がある
- 具体的な入力、状態、環境で再現または論理的に成立する
- 実害が説明できる
- 指摘位置が問題を理解するのに最適である
- 他の指摘と重複していない
- 単なる好みや過剰防御ではない

満たさない候補は、指摘から除外するか「要確認」に落とす。

### 7. 優先度を付ける

- **P0 Critical**: 即時対応が必要。広範な停止、重大なデータ損失、容易に悪用可能な重大脆弱性など。
- **P1 High**: マージ前に修正すべき。主要機能の破壊、権限逸脱、一般的条件での誤結果、不可逆な互換性破壊など。
- **P2 Medium**: 修正を強く推奨。限定条件での不具合、性能劣化、運用上の深刻な盲点、回帰防止テストの重要な欠落など。
- **P3 Low**: 影響は限定的だが修正価値がある。軽微な堅牢性や保守性の問題など。

セキュリティという理由だけで自動的にP0/P1にしない。到達可能性、必要権限、データ感度、被害範囲を考慮する。

## 指摘の書き方

1件の指摘には以下を含める。

- `[P0|P1|P2|P3]` と短い命令形または問題形のタイトル
- `path/to/file.ext:L10-L18` のような最小行範囲
- 問題が成立する入力・状態・環境
- なぜ誤りか、どのような影響があるか
- 最小修正方針
- 必要なら検証用テスト
- 確信度 `high | medium | low`

悪い例:

> エラーハンドリングを改善してください。

良い例:

> **[P1] 再試行時の二重課金を防ぐ**  
> `payments/service.ts:L84-L96`  
> タイムアウト後に同じ注文を再試行すると、外部APIへ新しい冪等性キーを送るため課金が重複します。ネットワーク応答だけ失われた場合に顧客へ二重請求が発生します。注文IDから安定した冪等性キーを生成し、再試行テストを追加してください。  
> Confidence: high

## 出力形式

`references/output-format.md` に従う。指摘を最初に重要度順で提示し、その後に総括を置く。
指摘がない場合は、明確に「重大な指摘はありません」と記載し、実施した検証と残存リスクを示す。

## 最終品質ゲート

出力前に確認する。

- すべての指摘が変更に起因しているか
- 各指摘に具体的な成立条件と影響があるか
- 行範囲が狭く正確か
- 優先度が影響と発生可能性に合うか
- 秘密情報や個人情報を再掲していないか
- 同じ原因を重複指摘していないか
- 指摘がなくても検証内容と残存リスクを伝えているか
